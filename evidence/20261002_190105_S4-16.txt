Test ID: S4-16
Title: HTTP method / verb tampering on /diagnose
Student: student4 (Information Retrieval & Security Assessment)
Specialization: API Security

Objective:
Test whether /diagnose accepts unexpected HTTP methods (GET, PUT, DELETE) that might bypass intended request validation built only for POST.

Input / Attack Scenario:
Send GET and PUT requests to /diagnose instead of POST.

Expected Behaviour:
405 Method Not Allowed for any non-POST method.

Actual Behaviour:
{
  "get": {
    "status": "ok",
    "http_status": 405,
    "headers": {
      "date": "Fri, 02 Oct 2026 13:28:09 GMT",
      "server": "uvicorn",
      "allow": "POST",
      "content-length": "31",
      "content-type": "application/json",
      "vary": "Origin"
    },
    "body": {
      "detail": "Method Not Allowed"
    }
  },
  "put": {
    "status": "ok",
    "http_status": 405,
    "headers": {
      "date": "Fri, 02 Oct 2026 13:28:09 GMT",
      "server": "uvicorn",
      "allow": "POST",
      "content-length": "31",
      "content-type": "application/json",
      "vary": "Origin"
    },
    "body": {
      "detail": "Method Not Allowed"
    }
  }
}

Observations:
GET and PUT requests to /diagnose were correctly rejected with HTTP 405 Method Not Allowed, with the Allow: POST header.

Conclusion:
HTTP method tampering was properly handled, and the endpoint accepts only the intended POST method.

Severity: Low
Severity justification: Method tampering acceptance is typically low-impact alone but indicates lax endpoint configuration.
